## Issue 10 — `doctor` and `sync` disagree on `.claude/settings.json` (drift loop) 🔴

**Severity**: high (false-positive drift reports break CI gating)
**Reproducible**: yes, every run

### Repro

```bash
agnostic-ai sync                   # exit 0, "synced"
agnostic-ai doctor                 # ✗ claude: drift
agnostic-ai doctor --fix           # → reconciled 1 file(s)
agnostic-ai doctor                 # ✓ clean
agnostic-ai sync                   # re-introduces the drift
agnostic-ai doctor                 # ✗ claude: drift  (loop)
```

### Diff between `sync` output and `doctor --fix` output

```diff
--- after sync
+++ after doctor --fix
@@ -46,7 +46,6 @@
       }
     ]
-
   },
```

`sync` emits an extra blank line at L49 of `settings.json` that `doctor --fix` strips. Two emit paths produce different bytes from identical input.

### Impact

- README pitches `agnostic-ai doctor` as the drift detector for CI. With this bug it false-positives on every clean repo right after `sync`. CI gate becomes unusable.
- Linked to filed #195 (trailing newline) but not the same: this is a mid-file blank, not a trailing one.

### Suspected root cause

Two code paths emit `settings.json`:

- `internal/adapters/claude/claude.go:181` (sync emit) — calls `emit.MarshalJSONIndent(doc) + "\n"`.
- Some doctor/check path that normalizes the same map with subtly different whitespace.

Find the doctor-side emitter and unify both call sites on the exact same byte-writer.

### Fix

- (a) Route both sync and doctor through one shared `emitClaudeSettings(doc) ([]byte, error)` helper.
- (b) Add a regression test: `sync → doctor` should report clean exit on a freshly synced repo, no exceptions.

## Issue 11 — README "byte-identical" claim is overstated 🟡

**Severity**: medium (docs accuracy / user trust)

### Quote from README

> `import claude` prefers `.claude/rules/*.md` (each file → one rule, byte-identical) and falls back to slicing `CLAUDE.md` on `## headings`...

### Reality

After a single import-then-sync round trip, every output file differs from the source by at least:

1. Two prepended lines: `<!-- Generated by agnostic-ai -->` + blank.
2. One appended trailing blank line.
3. Frontmatter keys re-ordered (#190) and indent changed (#191).
4. Quote style flipped (#193).

So "byte-identical" is false for any file that survives a sync. The promise holds only for the import direction in isolation. Sync clobbers it.

### Fix

- (a) Reword README to "content-preserving round trip — provenance marker and canonical formatting are applied on emit".
- (b) Once #190/191/195 land, the only remaining delta is the marker. Then claim becomes accurate modulo the marker, which is acceptable.

## Issue 12 — Target table in README misleads on native-path support 🟡

**Severity**: medium (user expectation management)

### Concrete cases

| Adapter output | Tool that actually reads it natively |
|---|---|
| `.claude/rules/*.md` | None. Claude Code requires `@.claude/rules/*` references inside `CLAUDE.md` to load these. |
| `.claude/settings.json` | Yes, Claude Code. ✅ |
| `.claude/agents/*.md` | Yes, Claude Code. ✅ |
| `.codex/config.toml` | No. OpenAI Codex CLI reads `~/.codex/config.toml` (user-home, not per-project). |
| `.codex/prompts/*.md` | No. Not in upstream Codex CLI spec. |
| `.agents/agents/*.toml` | No. Speculative community AGENTS.md spec; no shipped consumer reads it. |

The current ✅ column conflates "we emit a file" with "the tool loads it". A user enabling `codex` expects their hooks to fire in OpenAI Codex CLI; they will not.

### Fix

Add a "native | convention" column to the target table:

| Target | Skills | Native path? |
|---|---|---|
| Claude Code agents | `.claude/agents/` | native |
| Claude Code rules | `.claude/rules/` | convention (loaded via `@…` reference in CLAUDE.md) |
| Codex hooks | `.codex/config.toml` | convention (Codex CLI does not read project-local config) |

Or strike the ✅ for non-native paths until the upstream tool supports them.

## Issue 13 — `settings.json` has two sources of truth (split overlay) 🟡

**Severity**: medium (mental model / authoring confusion)

### Observation

For Claude target, hooks come from `.agnostic-ai/hooks/*.md`. All other `settings.json` keys (`statusLine`, `enabledPlugins`, etc.) live in `.agnostic-ai/overlays/claude.settings.json`. Output is the merge of both.

### Why it's confusing

- A new user opens `.agnostic-ai/` and sees `hooks/`, `agents/`, `rules/`, etc. Logical model: one spec dir per concept.
- They do not expect `overlays/`. It's not in the README's "Where the specs live" list (`CLAUDE.md` says: agents, skills, rules, hooks, mcps, commands — no mention of overlays).
- Editing `statusLine` requires knowing to open `.agnostic-ai/overlays/claude.settings.json`, which is target-specific (defeats the "write once for every CLI" pitch).

### Fix options

- (a) Document `overlays/` prominently in README and `AGNOSTIC_AI.md` template.
- (b) Add a `.agnostic-ai/statuslines/` (or similar) abstraction that emits to Claude's `statusLine` and to whatever Codex/Gemini equivalent exists. Round-trippable like hooks.
- (c) Long-term: model status line and plugin config as first-class agnostic concepts if any other adapter has equivalents.

Short-term: at minimum add an entry under "Where the specs live" in the AGNOSTIC_AI.md template.

## Issue 14 — Capability warnings are noisy and unactionable 🟡

**Severity**: low-medium (UX)

### Repro

Enable `aider` (which doesn't support hooks or commands) alongside claude+codex. Sync stderr:

```
! aider: hook not supported, skipped
! aider: command not supported, skipped
! aider: hook not supported, skipped
! aider: command not supported, skipped
```

Two issues:

- Duplicated: one line per hook spec and per command spec is emitted, not one per (target, kind) tuple. With 4 hooks and 10 commands × 1 target → 14 lines that say the same two things. With three unsupported targets and dozens of specs, this drowns the rest of sync output.
- No action: warning doesn't say `set on-unsupported: silent in agnostic-ai.yaml to suppress` or which spec file triggered it.

### Fix

```
! aider: 4 hooks skipped (target does not support hooks)
! aider: 10 commands skipped (target does not support commands)
  fix: set `on-unsupported: silent` in agnostic-ai.yaml to hide these
```

Group by (target, kind) tuple. Include suppression hint.

## Issue 16 — Hooks → multi-target schema mapping is undocumented 🟡

**Severity**: low (docs)

### What's missing

`.agnostic-ai/hooks/<name>.md` is a Markdown file with frontmatter. It renders to:

- `.claude/settings.json` under `hooks.{PreToolUse|PostToolUse|...}` with `matcher` + nested `hooks[].{type,command}` schema.
- `.codex/config.toml` under `[[hooks.PostToolUse]]` with TOML `matcher = "..."` + `command = "..."`.

Mapping is non-obvious. `docs/user/spec-format.md` covers the agnostic frontmatter but not how `event:`, `matcher:`, `command:` fields land in each target's native shape. Users authoring a new hook spec can't predict what `.claude/settings.json` and `.codex/config.toml` will end up containing.

### Fix

Add a per-spec-kind "what gets emitted" table to `docs/user/targets.md`. Example for hooks:

```
agnostic-ai frontmatter:
  event: PostToolUse
  matcher: Bash(git commit*)
  command: echo "tests please"

→ .claude/settings.json:
  hooks.PostToolUse[] = {
    matcher: "Bash(git commit*)",
    hooks: [{type: "command", command: "echo \"tests please\""}]
  }

→ .codex/config.toml:
  [[hooks.PostToolUse]]
  matcher = "Bash(git commit*)"
  command = "echo \"tests please\""
```

Document for every spec kind × every target.

## Issue 17 — `doctor` doesn't check cross-target body drift 🟡

**Severity**: low (would-be feature)

### Scenario

User edits `CLAUDE.md` directly (forgetting it's generated) to add a project note. Next sync clobbers the edit. If they don't sync for a while, `CLAUDE.md`, `AGENTS.md`, `GEMINI.md` can all silently drift apart from `AGNOSTIC_AI.md`.

### Fix

In `agnostic-ai doctor`, beyond per-target drift, also check that every target's root entry-point body equals `AGNOSTIC_AI.md`. Report cross-target drift separately:

```
Cross-target consistency:
  ✓ AGENTS.md matches AGNOSTIC_AI.md
  ✗ CLAUDE.md drifted (10 lines added since last sync)
    Run `agnostic-ai sync` to overwrite local edits, or move the edits into .agnostic-ai/AGNOSTIC_AI.md first.
```

Helps catch the "I edited the wrong file" footgun.

## Issue 18 — Spec name collision detection missing 🟡

**Severity**: low (currently theoretical, easy to hit)

### Scenario

Manuscript has skill named `fix`. If user adds agent named `fix` (or command, or hook), both emit to different paths (`.claude/skills/fix/SKILL.md` vs `.claude/agents/fix.md`) — fine. But Cursor flattens everything to `.cursor/rules/<name>.mdc`, and other adapters may too. Different kinds, same name = silent overwrite.

### Fix

`agnostic-ai validate` (or `doctor`) should check for name collisions across kinds and warn:

```
! Collision risk: spec name "fix" used as both skill and agent.
  Cursor (.cursor/rules/fix.mdc): only one will survive.
  Rename one or set outputs.cursor.skill-prefix: "skill-".
```

## Issue 19 — `globs:` patterns not validated against repo paths 🟡

**Severity**: low (silent failure mode)

### Scenario

Source rule has `globs: backend/modules/*/Domain/**/*.php`. Repo restructured — `backend/` becomes `apps/backend/`. Glob now matches nothing. Adapter still emits rule, target silently never applies it. No error, no warning.

### Fix

`doctor` could optionally check each rule's `globs:` patterns against the working tree:

```
! Rules with no matching files in repo:
    backend-domain-layer.md (globs: backend/modules/*/Domain/**/*.php — no matches)
  Either fix the glob or the rule will never load.
```

Off by default (some monorepos have intentionally unmatched globs for future features). Opt-in via `agnostic-ai doctor --check-globs`.

## Issue 20 — `import` doesn't capture arbitrary `.claude/*.sh` or sidecar files 🟡

**Severity**: low (scope clarification)

### Scenario

Manuscript's `.claude/settings.json` references `.claude/statusline.sh`. The shell script is part of the Claude Code config but is not modelled by agnostic-ai. After `import claude` + `agnostic-ai revert`, if the user then deletes their `.claude/` dir intending to fully regenerate from spec, the statusline shell script is lost.

### Mitigation options

- (a) Document scope: import captures rules, agents, skills, hooks, commands, settings overlay. Anything else under `.claude/` is your responsibility — git-track those files yourself.
- (b) Capture arbitrary referenced files: detect `.sh` / asset paths referenced from `settings.json` and stash them under `.agnostic-ai/overlays/claude.assets/`. Heavy; probably not worth it.
- (c) Add a `.agnostic-ai/assets/<target>/` opt-in mirror for arbitrary files. Sync copies them through verbatim.

Recommendation: (a) — document the scope boundary in `docs/user/getting-started.md` so users know to git-track helper files alongside their `.agnostic-ai/` source.

## Issue 21 — `.agnostic-ai/.sync-state` purpose, format, and lifecycle undocumented 🟢

**Severity**: low (docs)

### Observation

After `sync`, `.agnostic-ai/.sync-state` appears with `{"synced_at": ..., "files_changed": 125}`. Not documented in README, `spec-format.md`, or `configuration.md`. Users will see it in `git status`, wonder if it should be committed, what triggers its update, what its absence means.

Issue #136 (closed) added it to managed `.gitignore`. But there's still no docs on what it is and what consumes it.

### Fix

One short page in `docs/internal/` or a section in `docs/user/configuration.md`:

- What it stores (last sync timestamp, file count).
- What reads it (doctor uses it to detect "sync was run vs never run").
- Whether to commit it (no — already gitignored).
- Whether to delete it (safe — sync regenerates).

## Issue 22 — Skill helper file preservation is undocumented (positive finding) 🟢

**Severity**: low (docs gap, but works correctly)

### What works

Manuscript has:

```
.claude/skills/i18n-parity/check.mjs            (JS helper)
.claude/skills/tiptap-extension/templates/      (template files)
```

Both round-trip byte-identically through import → sync. This is the right behaviour and probably non-trivial to get right. But it's not advertised anywhere in the README.

### Fix

Add a one-paragraph note in `docs/user/spec-format.md` under "Skills":

> Skills may contain helper files (scripts, templates, fixtures) alongside `SKILL.md`. Any non-`.md` file under `.agnostic-ai/skills/<name>/` (and any nested directory) is copied verbatim to the same relative location under each target's skills dir. Useful for shipping check scripts that the skill references.

Tells users this is a supported feature instead of an accident.
