# Compare RTK and Caveman across a complete diagnostic task

The [runner](trio-evaluation.py) compares concise instructions, RTK, the Caveman response skill, and both. Each task asks a live Claude session to run one harmless failing test fixture and report its counts, failures, paths, and expected and actual values. Each failure has its own line linking its identifier, path, and values. It measures a complete diagnostic session, including skill loading. It does not test code repair or a production workload.

Two larger fixed transcripts cover one failure and two failures, including a Unicode path. A third, short transcript uses an unsupported command so RTK leaves it unchanged. Runs are paired by task and repetition, then shuffled with a recorded seed. Each case starts in a separate directory with fresh Claude settings. RTK history and recovery paths are redirected explicitly; on macOS RTK still reads its existing configuration. HOME is inherited unchanged.

## Prepare without provider requests

Build the current CLI after the tool built-ins have merged. The bundled skill is copied from a recorded revision so the generated copy can be checked against it. Review its sources and licenses first.

```sh
go build -o /tmp/trio-agnostic-ai ./cmd/agnostic-ai
python3 docs/internal/experiments/trio-evaluation.py --self-test
python3 docs/internal/experiments/trio-evaluation.py \
  --output /absolute/path/to/new-evaluation \
  --agnostic /tmp/trio-agnostic-ai \
  --agnostic-build-source current-main \
  --agnostic-build-commit "$(git rev-parse HEAD)" \
  --skill internal/builtins/data/caveman/skills/caveman
```

The default writes each configuration's `builtins` list, runs sync and sync check, and verifies the generated skill and hook. It records the exact CLI binary, build commit, YAML, generated bytes, source hashes, and versions. It makes no provider request. The output directory must be new. The runner requires the selected agnostic-ai CLI plus installed Claude Code and RTK binaries. `--claude` and `--rtk` can select their paths.

## Run the live comparison

Land the runner before collecting a published result. Run it from current main while local builds and checks are idle. Use a fresh output directory, the skill from the same recorded revision, and `--live`. The default runs 24 cases with `claude-haiku-5-5`, two repetitions, a $0.12 per-session limit, and a $2 total limit. Review those options before running. Supply existing Claude authentication through its supported environment without putting credentials in command arguments or files.

First run a separate four-case trial run with `--tasks short --repetitions 1 --live` and a fresh output directory. Keep it separate from the final 24 cases. It checks the skills and plugins actually loaded by Claude and the unchanged short command before committing to the complete comparison.

Every configuration uses the same Bash and Skill tools and the same host settings. The three bundled skills remain available in every configuration. Only the generated Caveman skill changes between the baseline and skill configurations. The runner records the skills and plugins loaded at startup and requires the same bundled plugins across cases. Unexpected personal plugins or skills fail the setup check. A failed check stops further requests and retains the failed row and its known cost.

The skill configurations explicitly request `/caveman` through the Skill tool. A passing result must show that the loaded skill came from the generated project directory and matches the pinned body. Effective skills, bundled plugins, model, and MCP servers are recorded.

The exact fixture command, its exact RTK spelling, and the Caveman skill are preapproved. These approval settings do not make other calls impossible. The study rules reject saved-output retrieval and any extra tool call. Zero recovery reads therefore cannot establish that recovery would never be needed. This is a comparison of tasks answerable from the visible summary. The separate runtime experiment tests exact recovery and missing stores.

## Read the result

A passing row requires one exact command execution, the expected tool sequence, a failed command with exit 7, every required fact linked to the correct failure, no contradictory facts, and a completed session without permission denial. RTK rows require one processor call through the exact emitted command. Supported Cargo tasks must show its replacement reply and one matching RTK execution. The short task must show an empty successful reply, no RTK execution, an unchanged command, and all original output. Tests with deliberately invalid results reject missing facts, repeated execution, wrong rewrites, denials, and incomplete sessions.

For future runs, the answer check accepts either “command failed” or the exact task command in backticks followed by “failed.” This check was revised after the `9932169b` final collection. That collection used the earlier runner and keeps its recorded rejection of `payment-caveman-1` and its original decision to exclude that comparison from successful-task claims, even though the independent answer review accepted the answer. The revision does not replace or rescore that collection.

`manifest.json` records the method, versions and source files. `results.json` keeps failures and incomplete attempts alongside successful rows. Input, cache creation, cache reads, and output tokens are separate. Missing usage stays unknown, with an explicit completeness flag. The CLI cost is a list-price estimate, not an invoice. Elapsed time includes host startup and all task requests. Exact executions, retry calls, and attempted recovery reads are recorded. Skill instructions, generated project context, and activation overhead remain in the session totals. Sync time is recorded separately from the session time. The cache of built-in source files can be shared between runs, so its timing is not a controlled performance comparison.

The runner reads accumulated usage from the final result. Assistant message blocks can repeat, and their output counters are placeholders. Check the final input and cache totals against unique message IDs, and check result totals against `modelUsage`, before publishing. See Claude's [usage accounting rules](https://code.claude.com/docs/en/agent-sdk/cost-tracking).

Raw events and hook inputs remain private in the output directory. They can contain local paths, session identifiers, and full tool input. Export the reviewed evidence into a new directory:

```sh
python3 docs/internal/experiments/trio-evaluation-export-test.py
python3 docs/internal/experiments/trio-evaluation-export.py \
  --source /absolute/path/to/private-evaluation \
  --output /absolute/path/to/new-public-export
```

The exporter selects evidence files, replaces private skill, plugin and model names and identifiers consistently, and rejects recognized credential data. It preserves public usage-field names and Caveman source files checked against the bundled revision. It keeps diagnostic facts, failures, missing usage, and both original and exported file hashes. It does not scan arbitrary prose for every possible private fact. Review the export before staging it, retain the private originals, and review answers independently before making a workload recommendation. Earlier debugging runs belong in a separate dataset and cannot be substituted for the final run.
