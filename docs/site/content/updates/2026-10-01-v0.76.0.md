## Upgrading from v0.75.0 {#actions}

Stop any running `sync --watch` before migrating or installing. For a rule that should use only `globs` or `paths`, remove its `scope` and move it out of any source folder that names an existing project directory. For example, move `.agnostic-ai/rules/src/typescript-conventions.md` to `.agnostic-ai/rules/typescript-conventions.md`, remove `scope: src` and keep `globs: ["src/**/*.ts"]`. Do this before package installation if postinstall runs sync. The selector union now makes a directory scope apply to the whole directory as well as matching files.

For a standalone binary on macOS or Linux, install this release explicitly:

```bash
agnostic-ai upgrade --version v0.76.0
```

This command does not load the project's `requires` value. Before syncing with the new binary, manually align any existing exact pin and release-pinned schema comment for every installation channel:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/Chemaclass/agnostic-ai/v0.76.0/docs/schemas/config.schema.json
requires: "0.76.0"
```

For a project dependency, make those config edits before updating the package and lockfile, for example:

```bash
pnpm add -D --save-exact agnostic-ai@0.76.0
# npm alternative: npm install -D --save-exact agnostic-ai@0.76.0
```

Add `-w` only for a pnpm workspace-root dependency. Editing the configuration first matters when your project's postinstall runs sync. Preserve a deliberate minimum or range that already accepts v0.76.0. Neither upgrade nor package installation edits `requires` or the schema URL for you. For a global npm install, use `npm install -g agnostic-ai@0.76.0`; other package-manager installs use their manager. A Windows standalone install can use `.\install.ps1 -Version v0.76.0`.

After migrating rules and installing, run:

```bash
agnostic-ai --version
agnostic-ai sync
agnostic-ai lint
agnostic-ai sync --check
```

Use the local runner, such as `pnpm exec agnostic-ai`, when the dependency is project-pinned. Review the generated diff, especially nested instruction files, settings and hooks. If a Claude environment spec already has `setup`, remove an equivalent hand-written worktree bootstrap hook to avoid running setup twice.

## What agnostic-ai changed

### Rule selectors now add to each other

`scope`, `globs` and `paths` are alternatives: any matching selector can make the rule apply. For example:

```markdown
---
name: typescript-conventions
scope: src
globs: ["**/*.ts"]
---

Keep exported types stable for callers.
```

This selects the whole `src` directory **and** matching TypeScript files elsewhere. To select only TypeScript files under `src`, remove `scope` and use `globs: ["src/**/*.ts"]`. Also move the spec to `.agnostic-ai/rules/typescript-conventions.md` if its current location under `rules/src/` would infer the existing project directory `src` as its scope. Removing frontmatter scope alone does not remove a folder-inferred scope.

Folders that do not name existing project directories remain organizational groups. Use `agnostic-ai explain --file src/example.ts --target cursor` to inspect Cursor's applicable rules. Each target still has its own activation limits; [scoped context](@/docs/scoped-context.md) explains where filtering becomes an always-loaded instruction.

### Model tiers keep roles stable across tools

Name a model role in `agnostic-ai.yaml`, then refer to it from agents, skills or settings:

```yaml
models:
  strong:
    claude: opus
    codex: gpt-5.5
    effort:
      claude: xhigh
      codex: high
  fast:
    claude: haiku
    codex: o4-mini
```

An agent can use the role without duplicating those choices:

```markdown
---
name: reviewer
description: Review changes for correctness.
targets: [claude, codex]
model: strong
---

Report defects with a concrete failing case.
```

Use model IDs available to your account. A `default` entry can cover targets without an explicit mapping; otherwise an unmapped target gets no model and lint warns. An unknown tier name remains a literal model ID. A same-named tier in `agnostic-ai.local.yaml` replaces the whole tier, so repeat every mapping you need there. Save the example as `.agnostic-ai/agents/reviewer.md` and run `agnostic-ai explain agents/reviewer.md` to see its resolved choices. See [model configuration](@/docs/configuration.md#models).

### Protect paths with each target's native edit controls

Place a settings spec such as `.agnostic-ai/settings/protected.yaml`:

```yaml
protected:
  paths: [.github/**, composer.lock]
  decision: deny
  reason: CI and the lock file change only through the maintainer.
```

Paths are relative to the project root. `ask` is the default decision; the example uses `deny` because Cursor CLI supports that decision.

| Target | What v0.76.0 writes | Limit that affects use |
|---|---|---|
| Claude Code | Native `Edit` permission rules | Supports `ask` and `deny`. |
| Codex | A `PreToolUse` guard for `apply_patch` | Hooks must be trusted and active. `ask` blocks with a request for confirmation. |
| Gemini CLI | A `BeforeTool` guard for `write_file` and `replace` | `ask` blocks with a request for confirmation. |
| Cursor | `Write` deny rules in `.cursor/cli.json` | CLI only; `ask` remains advisory. |
| Other targets | A coverage note | No enforced protection is emitted. |

These controls cover edit tools. Shell commands that write files can still change them. Codex and Gemini's generated shell guards need `sh` and `awk`; check the target's runtime, especially on Windows. In Codex, inspect `/hooks` and project trust before relying on a guard. [Protected paths](@/docs/spec-format/settings.md#protected-paths) documents the controls and accepted patterns.

### Share hook scripts and test the real command

Reference an existing executable script under `.agnostic-ai/scripts/` from a hook spec, for example `.agnostic-ai/hooks/guard.yaml`:

```yaml
name: guard
targets: [claude, codex]
event: PreToolUse
matcher: Bash
command: .agnostic-ai/scripts/guard.sh
```

Sync copies the script into each target's hook directory and rewrites the reference, preserving its bytes and permissions. `.agnostic-ai/scripts/<target>/guard.sh` can override the shared body. Event names and reply formats still need to match the target; copying a script does not translate its protocol.

Run sync to place the copied scripts. If that guard is meant to block force pushes, test it locally before relying on an agent to call it:

```bash
agnostic-ai hook run guard --target claude --bash "git push --force" --expect block
agnostic-ai hook run guard --target codex --bash "git push --force" --expect block --format json
```

`hook run` executes the command hook with target-shaped payloads, checks its matcher, timeout and decision, and exits nonzero for an expectation mismatch or execution error. It supports Claude Code, Codex, Gemini CLI, Trae, OpenHands, Goose and Augment. Non-command handlers are not executed, and asynchronous handlers are not judged as blocking guards.

For scripts that need edited file paths, `agnostic-ai hook paths` reads the event JSON from stdin and emits paths relative to the current directory. `--action` or `--json` includes change types such as deletion and rename; plain path output includes existing files. This avoids teaching each formatter every target's payload shape. See the [hook commands](@/docs/cli-reference/maintain.md#hook-run) for payload fixtures and supported events.

### Turn coverage notes into a project gate

Coverage notes explain where a target cannot represent a portable field. Projects can now fail sync on unaccepted notes and record a reason for deliberate differences:

```yaml
coverage:
  fail-on-notes: true
  accept:
    - target: [codex, gemini, cursor]
      kind: skills
      field: argument-hint
      reason: The hint is for Claude's skill picker; other tools use the description.
```

An acceptance matches the named target, kind and field; it does not enable the missing feature. LINT024 identifies stale acceptances. This gate applies to project sync, and sync restores outputs when an unaccepted note fails the run. See [coverage configuration](@/docs/configuration.md#coverage).

Sync also removes stale generated settings and permission entries while keeping unrelated user keys, and restores merged outputs when a later operation fails. Invalid MCP JSON now fails with a path instead of being replaced as though it were an empty file.

### Codex subtree rules and opt-in command policies

Rules with exact subtree selectors, such as `globs: ["services/payments/**"]`, now become nested `services/payments/AGENTS.md`. Filename filters such as `services/payments/**/*.ts` stay inline with a coverage note because Codex cannot load instructions conditionally for each edited file. Codex reads the instruction chain for its working directory, so start it in the subtree when you need that nested context. Set `outputs.codex.nested-glob-rules: false` to retain the inline layout.

Portable Bash permissions can also become Codex exec prefix policies when explicitly enabled:

```yaml
outputs:
  codex:
    exec-policies-from-permissions: true
```

For example, a settings rule `Bash(go test:*)` can produce a `go test` prefix policy. Prefix matching permits additional arguments; an exact `Bash(git push)` allowance cannot retain exact-command semantics and may also allow `git push --force`. v0.76.0 names that widening in coverage notes. Review the [Codex policy mapping](@/docs/targets/codex.md) before opting in. It also reports ignored project settings and agent sandbox fields instead of presenting them as effective restrictions.

### Claude worktree setup and other native fixes

A Claude-targeted environment spec's `setup` now runs once in each new worktree. If setup is managed elsewhere, set `x-claude.setup: false` in that environment spec. Removing an equivalent hand-written bootstrap avoids duplicate dependency installation. Managed `.worktreeinclude` also stops copying Claude runtime paths.

Gemini agent-local MCP servers now use the native `mcp_servers` key; an `x-gemini.mcpServers` override is renamed with a note. Cursor receives portable allow and deny permissions in `.cursor/cli.json`, with notes for `ask`, unmapped rules and multi-word commands it cannot preserve. Copilot agents and skills write back to existing native locations rather than creating duplicate files; instruction descriptions also reach native frontmatter.

The [complete v0.76.0 changelog](https://github.com/Chemaclass/agnostic-ai/blob/v0.76.0/CHANGELOG.md#v0760---2026-10-01) lists the remaining fixes.

## What changed in the targets

### VS Code prefers portable MCP configuration

**VS Code 1.140, released September 30, 2026**, changes the preferred workspace MCP file to root `.mcp.json`. The legacy `.vscode/mcp.json` is deprecated and remains readable for compatibility. v0.76.0 documents this change and keeps agnostic-ai's existing `.vscode/mcp.json` default; it does not automatically migrate your MCP file. The existing opt-in is:

```yaml
outputs:
  copilot:
    root-mcp-file: .mcp.json
```

Use it when you want the portable root MCP file as well, then review the sync diff. This support predates v0.76.0; the release adds guidance for the vendor's new preference. [VS Code 1.140 notes](https://code.visualstudio.com/updates/v1_140), [MCP configuration formats](https://code.visualstudio.com/docs/agent-customization/mcp-servers#configure-the-mcpjson-file).

### Kiro adds native workflow recipes

Kiro's **September 30, 2026** updates add reusable workflow recipes, including IDE 1.2.4 and Kiro Web. Workflows are opt-in and can use native files under `.kiro/workflows/`. If you adopt them, maintain those recipes as Kiro configuration: v0.76.0 has no portable workflow spec, recipe emitter or recipe importer. `x-kiro` agent metadata configures an agent; it does not create a workflow recipe. [Kiro IDE release notes](https://kiro.dev/changelog/ide/1-2/), [Kiro Web workflow announcement](https://kiro.dev/changelog/web/introducing-workflows/).
