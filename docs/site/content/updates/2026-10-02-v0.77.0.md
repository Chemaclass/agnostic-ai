## Upgrading from v0.76.0 {#actions}

1. **Stop existing watchers and check macOS compatibility.** Stop `sync --watch` before a package install can start another sync. Prebuilt binaries now require macOS 13 or newer; macOS 12 needs the source-build command in step 4.
2. **Check rules with narrow `globs`.** When `alwaysApply` is absent, those rules now request conditional activation. Add `alwaysApply: true` to each rule you intended to load unconditionally. A catch-all such as `**/*` stays always on. Tools that cannot express a file filter still have the limits described in [scoped context](@/docs/scoped-context.md).
3. **Fix config keys that were previously ignored.** Unknown keys and misspelled targets now stop config loading. Correct them before an install hook runs sync, including keys in `agnostic-ai.local.yaml`. The new error names the file, line, and closest key if one remains.
4. **Update the project pins, then install through the same channel.** If `agnostic-ai.yaml` pins `requires: "0.76.0"`, change it to `"0.77.0"` and move a versioned schema URL to the `v0.77.0` tag. Keep an intentional minimum or range if it already accepts this release. For a standalone binary, run `agnostic-ai upgrade --version v0.77.0`; for npm, update the exact dependency and lockfile with your package manager. On macOS 12, use Go 1.26.8 or a newer 1.26 patch with `GOTOOLCHAIN=local go install github.com/chemaclass/agnostic-ai/cmd/agnostic-ai@v0.77.0`.
5. **If you re-import MCP servers, set the variables import names.** Project imports now replace literal `env` and `headers` values with references. This includes plain values such as `NODE_ENV: production`; restore a non-secret literal deliberately or provide its variable. Continue IDE users must put secrets in an ignored `.env` file, rather than relying only on the shell environment.
6. **Regenerate and review the output, then restart watchers.** If generated files are committed, include their changed bytes with the config and dependency pins.

```bash
agnostic-ai sync --plan
agnostic-ai sync
agnostic-ai sync --check
agnostic-ai lint
```

## What agnostic-ai changed

### Add another tool with one command

`use` replaces the manual sequence of adding a target, importing its native config, syncing, and finding the files it reads:

```bash
agnostic-ai use codex
agnostic-ai use claude codex cursor
```

In an existing project, it imports a newly added tool's own config before generating output, so a hand-written `AGENTS.md` can become shared source. In a new project, it also creates `agnostic-ai.yaml` and adopts the detected tools. The result names each tool's instructions, skills, agents, hooks, and MCP paths. A conflict with a protected spec stops the import and names the decision you need to make. `use` configures tools; you launch their CLIs as usual. [Command reference](@/docs/cli-reference/start.md#use).

### File rules follow their patterns by default

A rule such as `globs: "src/**/*.tsx"` without `alwaysApply` used to be always on in some targets and conditional in others. v0.77 requests conditional activation consistently wherever the target has that field. An explicit `alwaysApply: true` still requests unconditional activation. This fixes the default without changing the selector union introduced in v0.76: a directory scope still adds every file in that scope. [Rule fields](@/docs/spec-format/rules.md#fields).

### Imports and sync protect work already on disk

- Import previews now show each destination and conflict with `agnostic-ai import claude --dry-run --diff`. A real import refuses to replace a changed existing spec the source tool never read, unless you choose `--overwrite`. New instruction sections are added to `AGNOSTIC_AI.md` instead of replacing its whole body.
- Sync stops before replacing a hand-written instructions file that has not been imported. For an edited generated file, a normal sync saves a `.bak` before writing the spec's version; `--keep-edits` keeps the edit instead. An existing backup is preserved.
- `sync`, `import`, `init`, and `use` take one project lock. A second writer names the running command and its process ID. A watcher holds that lock until it exits, so stop it before a separate writing command.

These checks make adding a tool and moving native edits back to source reviewable. [Import behavior](@/docs/cli-reference/start.md#import), [hand edits](@/docs/cli-reference/sync.md), [concurrent commands](@/docs/cli-reference/_index.md#concurrent-commands).

### Absolute source directories work throughout the workflow

Projects that keep shared specs outside the checkout can use the same paths for import, preview, sync, validation, and watch:

```yaml
sources:
  rules: /srv/team-specs/rules
  skills: /srv/team-specs/skills
```

Imports write to those configured directories; previews name those destinations without writing to them. Watch includes external roots, and validation checks their specs. The shared directories must exist on each machine that uses the config. [Source paths](@/docs/configuration.md#sources).

### Codex model aliases work inside your existing tiers

Model tiers were added in v0.76. v0.77 adds Codex aliases, resolves them to explicit IDs when writing output, and shows the resolution in `explain`:

| Alias in a spec or tier | ID written by v0.77.0 |
|---|---|
| `sol` | `gpt-6.1-sol` |
| `luna` | `gpt-6-luna` |
| `astra` | `gpt-6-astra` |

```yaml
models:
  strong: {claude: opus, codex: sol, effort: high}
  fast: {claude: haiku, codex: luna, effort: low}
```

An agent with `model: strong` uses the corresponding target's model. Exact IDs remain available when you want to hold a model steady. Each agnostic-ai release fixes its alias table; a later upgrade that moves an alias prints a note on the first writing sync. Shared Claude-only model names also get clearer coverage notes when another target cannot use them. [Model tiers and aliases](@/docs/configuration.md#models).

### MCP credentials stay out of imported project specs

Project import replaces credentials with portable `${NAME}` references, and sync translates those references to each tool's native form. If a tool cannot express a reference in that field, sync omits it and names the gap instead of writing it as literal text. Continue gets its `{% raw %}${{ secrets.NAME }}{% endraw %}` form and resolves IDE secrets from `.env` files. Explicit literals you write yourself still stay literal.

Claude Code MCP import and sync also preserve both `true` and `false` for `alwaysLoad` and `bareElicitationCapability`. This matters because `alwaysLoad: false` has a different meaning from omitting the flag. [MCP references and target options](@/docs/spec-format/mcps.md#environment-references).

### Checks and automation report the failure you need to fix

`sync --check --plan` now exits non-zero on drift, so CI can gate on the short plan. Likely hook-event typos stop sync before writing; likely agent skill-name typos get a warning. A failing `sync --json` keeps information about files an adapter wrote before failing, and CPU profiles are saved even when the command fails. Kiro validation accepts `SessionEnd` and suggests `SessionStart` for the legacy `AgentSpawn` alias.

All smaller fixes and documentation changes are in the [v0.77.0 release notes](https://github.com/Chemaclass/agnostic-ai/releases/tag/v0.77.0).

## What changed in the targets

### Claude Code: MCP tool loading and handshake compatibility

Claude Code 2.1.287 (October 1) adds forced MCP tool deferral and a compatibility flag for servers using an older elicitation handshake. v0.77 preserves these settings through import and sync. For a server that needs both behaviors:

```yaml
x-claude:
  alwaysLoad: false
  bareElicitationCapability: true
```

The first keeps all server tools behind tool search; the second opts into the documented compatibility handshake. Omit either flag to retain Claude Code's default. Other targets omit these Claude-only flags. [Claude Code release notes](https://github.com/anthropics/claude-code/releases/tag/v2.1.287).

### Claude Code: executable Mods and repository check skills

**Mods arrive in 2.1.287, released October 1.** JavaScript or TypeScript handlers can change tool calls, prompts, and the interface inside Claude Code. Existing agnostic-ai skill assets can carry a plugin manifest and its module files into `.claude/skills/`; a Settings spec can enable that skills-directory package:

```yaml
x-claude:
  enabledPlugins:
    team-mod@skills-dir: true
```

This uses the existing asset and settings routes. Portable Hook specs still describe their own hook types. Mods run outside the Bash sandbox, so inspect the module code before enabling it. Check `claude --version`: a channel still on 2.1.285 does not have this feature. [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview).

**Repository `verify` and `simplify` skills are selected at session start in 2.1.286, released September 30.** Claude's commit instructions ask it to run eligible skills before committing, except for changes limited to docs or tests. Put your team's checks in a portable skill with one of those names and sync it. Model invocation and Git instructions must remain enabled. This requests a check from the assistant; use a Git hook or CI when passing the check must be enforced. [Claude skills reference](https://code.claude.com/docs/en/skills#run-your-checks-before-each-commit).

### Kiro: background workflows need native recipe files

Kiro's September 30 release (IDE 1.2.4 and CLI 2.26.0) adds opt-in workflows for repeatable background tasks. The recipes are step graphs stored as `.kiro/workflows/*.workflow.json`, `.workflow.yaml`, or `.workflow.yml`. Enable the feature in Kiro and author the recipe in that native format. agnostic-ai's Agent kind writes agent Markdown and does not generate these graphs. [Kiro release notes](https://kiro.dev/changelog/), [workflow authoring](https://kiro.dev/docs/workflows/authoring/).

The October 2 audit also corrected an inheritance assumption: listing `x-kiro.resources` does not by itself remove default steering, skills, or `AGENTS.md`. Kiro's `chat.disableInheritingDefaultResources` controls that behavior. v0.77 keeps steering copies when an agent lists resources, so review both sources if your agent's context contains repeated rules. [Custom-agent resources](https://kiro.dev/docs/custom-agents/configuration-reference/).

### Cursor: Bugbot settings and shared skills have separate controls

The October 2 audit verified `.cursor/config/bugbot.yaml` as repository-wide Bugbot service policy, read from the default branch. Use it for review frequency, draft reviews, effort, and autofix settings. agnostic-ai writes `.cursor/BUGBOT.md` review instructions; it does not emit or import the service YAML. Keep that file under native management when you need those controls. [Bugbot reference](https://cursor.com/docs/bugbot).

Cursor also reads the shared `.agents/skills/` tree where the Codex target writes skills. Turning off **Include Third-Party Plugins, Skills, and Other Configs** stops compatibility imports but does not disable this native shared-directory discovery. Inspect the shared tree when deciding which skills Cursor should see. [Cursor skills](https://cursor.com/docs/skills).

### Copilot CLI: hooks inherit an enabled session sandbox

The hooks reference checked October 2 says repository command hooks run within the enabled session sandbox. A hook's `cwd` or `env` does not grant access to more paths. If an existing guard now fails on an external directory, adjust the native sandbox grants rather than only changing its emitted hook metadata. Administratively managed hooks have separate host execution rules. agnostic-ai's hook output continues to use the documented format. [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference).

### Factory: image selection is independent of the coding model

Factory's settings reference checked October 2 documents a separate `imageGenerationModel` selection, bounded by organization image policy. Choose the image model through an existing Settings spec's `x-factory.imageGenerationModel`; changing a portable coding-model tier does not select it. Sync can emit the field, but its import round trip is not supported. [Factory settings hierarchy](https://docs.factory.com/enterprise/hierarchical-settings-and-org-control).

Factory CLI 0.232.0 and Desktop 0.189.0 (October 2) also keep project- or organization-declared marketplaces under the declaring settings. To remove one, change that declaration; deleting it in the marketplace manager alone is insufficient. Native marketplace declarations can already pass through `x-factory` settings. [Factory release notes](https://docs.factory.com/changelog/release-notes).

### Codex: Guardian context controls remain experimental

Codex 0.160.0 (October 1) adds controls for giving Guardian conversation history and root handoff context when reviewing actions. The released `guardian_conversation_history_tools` and `guardian_root_handoff_context` flags are experimental and off by default. Existing Codex TOML overlays can preserve native settings, but agnostic-ai neither enables these flags nor adds a portable approval setting for them. [Codex release notes](https://github.com/openai/codex/releases/tag/rust-v0.160.0), [released feature definitions](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/features/src/lib.rs).
